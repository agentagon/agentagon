# Assess evals and prepare a benchmark

Use this procedure inside Audit, including dataset-only and issue-coverage requests. The host assesses evidence; Python preserves the assessment and input identity. Do not infer dataset quality from a universal score or from a passing agent run.

1. Inspect documented eval entry points, configuration, test fixtures and dataset loading code. File names are discovery hints only. Resolve the selected agent or issue to explicit dataset and entrypoint files. Report exclusions and incomplete discovery.
2. Inspect representative cases and labels against requirements and trusted references. Assess `coverage`, `label_correctness`, `duplicates`, `representativeness`, `provenance`, `leakage` and `sensitivity`. Use `supported`, `concern` or `unknown`, a rationale, and concrete evidence. A narrow issue audit covers its relevant behaviors; it cannot establish complete application coverage. Never invent labels or call observed model outputs ground truth.
3. Write an assessment JSON in ignored `.agentagon/` storage with `goal`, `author`, `dataset_paths`, `entrypoint_paths`, `assessments`, `proposed_cases`, and optional saved `issue_ids`. Paths are explicit checkout-relative files, not directories. Each assessment is `{ "status": "unknown", "rationale": "...", "evidence": [] }`; supported/concern assessments need evidence entries with `path` and `detail`. Use the task context’s `resources` paths to locate the benchmark assessment contract. Include a valid existing evaluation `plan` only when its expectations, metrics and execution are established.
4. Run `agentagon _internal --workspace CHECKOUT benchmark draft --assessment ASSESSMENT_JSON`, adding `--audit AUDIT_ID` when linked to a saved audit. The draft records immutable content references without requiring Git, an execution profile or permission to run the application. Retain its ID in the audit result. With no usable dataset, save proposed cases and follow the shared [authoring confirmation gate](../../eval/references/authoring.md) before creation/running, unless already explicitly requested.
5. Inspect `benchmark status BENCHMARK_ID`. Readiness is separate from assessment completion. Missing checks, Git, execution profile, permissions or limits must remain visible. A dataset and a draft are not yet a validated frozen benchmark.
6. When inputs still match and execution is ready and authorized, run `benchmark prepare BENCHMARK_ID --profile NAME --budget BUDGET_JSON --author AUTHOR`. Continue with the returned evaluation draft and the [evaluation preparation procedure](../../optimize/references/evaluation.md), including baseline, known incorrect cases and independent review. Identical retries resume that evaluation and its existing budget. Changed limits or settings require an explicitly new draft (`benchmark draft --assessment ASSESSMENT_JSON --new`), with authorization for new execution limits; never use renewal to evade a failed check or review. A changed committed source gets a new draft identity. Audit may prepare existing evals and confirmed missing eval creation. Keep intended harness and eval source in the repository, and private inputs in ignored storage.
7. Report the dataset scope, gaps, proposed cases, benchmark ID, preparation state, blockers and any measured baseline. If blocked, finish the assessment and preserve the draft for continuation. A `historical_baseline` belongs to the recorded revision; current source/input blockers still apply. Do not mark a draft ready merely because its inputs were saved.

For authorized dataset repair, the shared procedure creates a new evaluator version and compares grounded coverage, label corrections and sensitivity at a fixed application revision. Keep an active application's frozen benchmark unchanged. A changed dataset score cannot establish application improvement.
